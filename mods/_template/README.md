# example-mod

One line on what this mod does and how a player notices it. The launcher shows this line
for a mod that has no `tools/lib.mjs` `MOD_META` entry yet, so keep it a real sentence —
and replace it with yours. (Copied this folder with `node tools/lclite.mjs new <name>`?)

> **This folder is LCLite's layout example.** It is a complete, working mod — not a stub:
> a `files/` payload (a page script) plus the one hunk that loads it. `node
> tools/lclite.mjs new <name>` copies it under your name, rewriting `example-mod` and
> `exampleMod` everywhere. The full workflow, and what the launcher does with each part:
> [docs/MAKING-A-MOD.md](../../docs/MAKING-A-MOD.md).

## Layout — the whole contract

```
mods/example-mod/
├── README.md                      this file — update it in the SAME commit as any
│                                  behaviour change (FOR_AGENTS_README.md rule 9)
├── files/                         the PAYLOAD — copied verbatim into the tree
│   └── engine/public/lclite/example-mod/
│       └── ui.js                  → <install>/engine/public/lclite/example-mod/ui.js
└── patches/                       the HUNKS — one directory per revision
    └── 289/                       the primary revision (revs.json)
        └── client_ejs.json        → adds the version-keyed <script> tag that loads ui.js
```

A mod delivers through two independent lanes, and a folder may ship either or both:

| lane | what it is | which revisions it works on |
|---|---|---|
| `patches/<rev>/*.json` | `{find, replace}` anchors into the upstream sources — **generated by `regen`, never hand-written** | one corpus per revision, or one it `inherits` ([docs/REVS.md](../../docs/REVS.md)) |
| `files/**` | files copied verbatim: `files/<repo path>` → `<repo path>` | every revision, no anchors to rot |

`apply` installs both together and strips both together: the payload is copied and the
hunks are inserted, or (unticking the mod, or applying without it) the hunks are reversed
and the copied files are removed. Nothing else is needed — no registry, no manifest edit,
no panel edit. Drop the folder into `mods/` and the launcher lists it.

Two things that are *not* mods, and why the folder rule exists: a directory under `mods/`
whose name starts with `_` or `.` is skipped by every reader (these tools and the
launcher). That is what keeps this template out of the player-facing mod list while
staying inside the repo where authors will find it.

## The hunk — and why it looks like that

`patches/289/client_ejs.json` is one hunk: three pristine lines of `engine/view/client.ejs`
(the body opening — `<body>`, `<center>`, the canvas div), with the script tag inserted
right after `<body>`.

- **The first added line is the marker**, `<!-- lclite:example-mod -->` (HTML comment in
  EJS; `// lclite:<mod>` inside page scripts). `regen` routes hunks by marker with 100%
  precision, so the marker is what makes this file *this mod's* patch. Every added block
  needs one.
- **The `?v=1` is not decoration.** Page assets are version-keyed because browsers re-serve
  a stale disk copy of a plain path past a hard refresh. Bump it (and `VERSION` in
  `ui.js`) in the same commit as a change to the asset.
- **The site is free, and that is the point.** A hunk inserts into a *gap* between two
  pristine lines; two mods inserting into the same gap become ONE diff island, and `regen`
  then reports `MIXED MARKERS` and lets one mod swallow the other's block. The tail of
  `client.ejs` belongs to `mods/tcg`, which is why this example hangs off `<body>` — and
  why the anchor is three lines rather than a window wide enough to span somebody else's
  insertion. `node tools/selfcheck.mjs` checks both (the anchor still matches with every
  other mod applied, and no other mod uses this gap).

If your mod needs no page script, delete this hunk and the `patches/` directory: a
payload-only mod is a valid mod, and it works on every revision because it has no anchors.

## Settings contract

- **One key, your own, camelCase**: this mod's is `exampleMod` (in `ui.js`).
- Read it at YOUR hook site — here, wherever the page script runs; for an engine mod, at
  its own per-frame hook. Never read another mod's key and never route settings through a
  shared hub (rule 5): that is what lets your hunks fail on a new revision without
  silently killing everyone else's toggles.
- A panel row is optional: without one, the F1 panel synthesizes a row from
  `installed.json` (name = folder name, description = your settings rows). To ship a real
  one, add to `MOD_REGISTRY` in
  `mods/control-panel/files/engine/public/lclite/panel.js`:

  ```js
  { id: 'example-mod', name: 'Example mod', desc: 'One line, same as MOD_META.',
    master: { key: 'exampleMod', def: 'false' } }
  ```

  ...then bump that panel's own `?v=` in `engine/view/client.ejs` — a returning player
  otherwise keeps the cached panel and your row is missing. And add a `MOD_META` entry to
  `tools/lib.mjs` with the SAME wording (`doctor` prints a note when the two drift).

## How this mod was made (the loop every mod follows)

1. `node tools/lclite.mjs new example-mod` — this folder, working, before any edit.
2. Edit the tree: `LCLITE_ROOT=<install>` for the hunks, `files/` for the payload. Every
   added block starts with a marker.
3. `LCLITE_ROOT=<install> node tools/regen.mjs` — turns the tree's diff into
   `patches/<rev>/*.json`. Add your patched files to `MODS` in `tools/regen.mjs` first if
   no other mod diffs them (a file nothing lists is silently never extracted).
4. `LCLITE_ROOT=<install> node tools/lclite.mjs apply --check` → `✗0`, then
   `apply` (copies the payload, inserts the hunks, rewrites `installed.json`).
5. Prove it: `node tools/doctor.mjs` (exit 0) · `node tools/matrix.mjs` (every declared
   revision still takes the corpus) · `bash tools/acceptance.sh` (pristine clones at the
   pinned revs reproduce the live tree byte-for-byte, then a converge round-trip is
   byte-stable) · `node tools/lclite.mjs build` if any TypeScript changed.
6. Commit the overlay only — never the modded upstream trees (rule 6).

## What a page script can and cannot do

`ui.js` runs in the page's realm beside `panel.js`: DOM, CSS, `localStorage` and
`window.lostcityClient` are all fair game, and `console.log` works even in a production
build (bundled mods lose their logs). What it cannot do is reach into the client's
internals — drawing, input, packets, interfaces. That needs a hunk in the TypeScript
sources and a rebuild: the other lane, walked through in
[docs/MODS.md](../../docs/MODS.md) §TYPE B.
