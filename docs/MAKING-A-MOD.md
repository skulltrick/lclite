# Making a mod

LCLite is a folder scan. A mod is a directory under `mods/`, and the launcher lists
whatever it finds there — no registry to edit, no manifest to regenerate, no panel
change required. Drop the folder in, tick it in the launcher, press **Apply changes**.

This page is the on-ramp: what a mod folder is, what each part does, and the loop that
proves it works. The deep guide (hook-site table, the panel↔engine contract, TYPE C
entity blueprint, terser law) is [MODS.md](MODS.md); revisions are [REVS.md](REVS.md).

```
node tools/lclite.mjs new my-thing        # a complete, working mod — right now
node tools/lclite.mjs list                # what every mod folder resolves to
node tools/selfcheck.mjs                  # the drop-in contract, asserted
```

---

## 1. The folder is the mod

```
mods/my-thing/
├── README.md                     what it does + why (rule 9: same commit as any change)
├── files/                        THE PAYLOAD — copied verbatim into the tree
│   └── engine/public/lclite/my-thing/
│       └── ui.js                 → <install>/engine/public/lclite/my-thing/ui.js
└── patches/                      THE HUNKS — one directory per revision
    └── 289/                      the primary revision (revs.json)
        └── client_ejs.json        the anchor that loads ui.js into the page
```

A mod delivers through two independent lanes, and it may ship either or both:

| lane | what it is | which revisions it works on |
|---|---|---|
| `patches/<rev>/*.json` | `{find, replace}` line arrays anchored into the upstream sources — **generated by `regen`, never hand-written** | one corpus per revision, or one it `inherits` ([REVS.md](REVS.md)) |
| `files/**` | files copied verbatim: `files/<repo path>` → `<repo path>` | every revision — nothing to rot |

`apply` installs both together and `uninstall` reverses both: hunks inserted, payload
copied, or hunks reversed and copied files removed (empty directories are pruned too, so
a strip is a real inverse). A folder with neither lane is not installable, and `doctor`
says so.

**Two folder names are not mods**: a directory under `mods/` whose name starts with `_`
or `.` is skipped by every reader — these tools, the launcher, and the acceptance
harness. That is deliberate, and it is what lets [`mods/_template/`](../mods/_template)
live in the repo as the layout example without ever appearing in a player's mod list,
being applied by a bare `apply`, or being audited as a corpus. Use it for scratch mods
too.

## 2. Start from the layout example

```
node tools/lclite.mjs new my-thing
```

That copies [`mods/_template/`](../mods/_template) under your name, rewriting the id
everywhere it appears — folder and file names, the `lclite:<mod>` markers, the payload's
own version stamp, the README. **What comes out is a working mod, not a stub**: a page
script that logs a line, and the one hunk that loads it. Apply it and it runs.

Read `mods/_template/README.md` when you are done here — it is the same layout annotated
file by file, and it is what your new mod's README starts as.

## 3. What the launcher does with it

| step | what happens |
|---|---|
| discovery | the launcher scans `mods/` (Go: `listModsFromOverlay`) — any real folder is a mod, this instant, no restart needed beyond reopening the page |
| label | `tools/lib.mjs` `MOD_META` if it has an entry; otherwise the **folder name** |
| description | `MOD_META`'s `desc`; otherwise the **first non-heading line of the mod's README** — so a dropped-in folder reads sensibly before anyone writes metadata for it |
| available? | it has hunks for the install's revision (own corpus or an inherited one) **or** a `files/` payload. Otherwise the row is greyed with "not on this revision" — a mod is all-or-nothing per revision, never half-applied |
| apply / remove | one *Apply changes* button, convergent: ticked mods are applied, unticked mods are stripped. The launcher shells out to `node tools/lclite.mjs --mods <ticked>` — one implementation, never a second one in Go |
| in-game | `apply` writes `engine/public/lclite/installed.json`; the F1 panel lists the mods in that file, and a mod the panel has no `MOD_REGISTRY` entry for gets a **synthesized row** (name = folder name, description from its settings rows) so it appears with zero panel edits |

Nothing here needs a registry entry. `MOD_META` (in `tools/lib.mjs`) is presentation only:
add it when you care about the label, and make the wording **identical** to your F1 panel
row — `doctor` prints a note when the two drift apart.

## 4. The loop

```sh
# 0. baseline — abort and report if this is not clean
LCLITE_ROOT=<install> node tools/doctor.mjs                  # exit 0
LCLITE_ROOT=<install> node tools/lclite.mjs apply --check     # ✗0 on every mod

# 1. scaffold
node tools/lclite.mjs new my-thing

# 2. build it
#    payload only  → edit mods/my-thing/files/**            (no build, no TypeScript)
#    client behaviour → edit <install>/webclient/src/… or <install>/engine/view/…,
#                       starting every added block with a marker: // lclite:my-thing
#                       (<!-- lclite:my-thing --> in EJS's HTML regions)

# 3. snapshot the hunks (skip if you only touched files/)
#    first add 'my-thing': ['<file>', …] to MODS in tools/regen.mjs if no other mod
#    diffs that file — a file nothing lists is silently never extracted
LCLITE_ROOT=<install> node tools/regen.mjs

# 4. apply it (re-copies statics, inserts hunks, rewrites installed.json)
LCLITE_ROOT=<install> node tools/lclite.mjs apply --no-build
#    ...or, exactly what the launcher does:
LCLITE_ROOT=<install> node tools/lclite.mjs --mods my-thing,control-panel

# 5. prove it
LCLITE_ROOT=<install> node tools/doctor.mjs                   # exit 0
node tools/matrix.mjs                                         # every declared revision still takes it
bash tools/acceptance.sh                                      # pristine clones reproduce the tree byte-for-byte
LCLITE_ROOT=<install> node tools/lclite.mjs build             # only if TypeScript changed
```

Two rules in step 2 and 3 that cost real time when they are missed:

- **A file nothing lists in `regen.mjs`'s `MODS` is never diffed** — your edit produces
  no hunk, and `apply --check` stays green because there is nothing to check. New patched
  file = new entry in `MODS`.
- **A marker line is what makes a block yours.** `regen` routes hunks by
  `lclite:<mod>` with 100% precision; a block without one falls back to a regex guess
  that only warns. Every added block, every time.

## 5. Which lane do I need?

| you want to… | lane | cost |
|---|---|---|
| add DOM chrome, page CSS, a HUD built from page assets, read `window.lostcityClient` | **payload** (`files/`) | none — `apply` copies it |
| change what the client *draws*, *reads* or *sends*: rendering, input, packets, interfaces, camera | **hunks** into `webclient/`/`engine/` TS | a bundle rebuild (`lclite.mjs build`) |
| put a control in the F1 panel | a `MOD_REGISTRY` row (panel.js) + a `localStorage` key your mod reads | bump the panel's `?v=` |
| fake entities / model overrides (TYPE C) | payload code + ONE import hunk | rebuild |

A page script runs in the page's realm next to `panel.js`: DOM, CSS, `localStorage` and
`window.lostcityClient` are fair game, and `console.log` survives a production build
(bundled mods lose their logs). It cannot reach into the client's internals — that needs
a hunk and a rebuild. Hook sites for every common one (the render pass, a click, a
keypress, an interface component, the minimap widget) are tabulated in
[MODS.md](MODS.md) §TYPE B.

**Put pure logic in the payload, not in the hunk.** Anything that does not need client
state — a settings parse, a decision table, geometry — ships as
`files/webclient/src/<mod>/…` and is pulled in by one import hunk, so a bun harness can
import the REAL shipped file and test it headlessly (`mods/hotkeys`, `mods/true-tile`,
`mods/ground-items` all do this).

## 6. Settings, and the panel row

- **One key, your own, camelCase, mod-prefixed** — e.g. `myThing`. Read it at YOUR hook
  site, per frame. Never read another mod's key, never route settings through a shared
  hub (rule 5): that is what lets your hunks fail on a new revision without silently
  killing everyone else's toggles.
- **A panel row is optional.** Without one, the F1 panel synthesizes a row from
  `installed.json`. To ship a real one, add to `MOD_REGISTRY` in
  `mods/control-panel/files/engine/public/lclite/panel.js`:

  ```js
  { id: 'my-thing', name: 'My thing', desc: 'One line — same wording as MOD_META.',
    master: { key: 'myThing', def: 'false' } }
  ```

  ...and **bump that panel's own `?v=`** in the live `engine/view/client.ejs` (hand-edit →
  `regen` → `apply`, same commit). Without the bump a returning player keeps the cached
  panel and your row is missing. Every page asset is version-keyed for this reason —
  browsers re-serve a stale copy of a plain path past a hard refresh.
- More settings = rows in `MODS` in the same file (`toggle`, `slider`, `select`,
  `color`, `action`, `text`); sliders need an explicit `key:`. Add your keys to the
  *Reset all* clear-list (grep `reset-all`).

## 7. Removing a mod

Three ways, all the same engine:

```sh
# in the launcher: untick it and press Apply changes (applying is convergent)
LCLITE_ROOT=<install> node tools/lclite.mjs --mods control-panel,gpu    # this set, nothing else
LCLITE_ROOT=<install> node tools/lclite.mjs uninstall                   # everything off, pristine
```

A strip removes the hunks and the copied payload files (only when the tree copy still
matches the overlay byte-for-byte — a file you edited in the tree is kept and reported).
Then delete the folder from `mods/` when you no longer want it listed.

Retiring a mod that other installs already have applied needs one reset: the deleted
corpus can no longer reverse its own hunks, so those installs report `anchor not found`
until they are reset to pristine and re-applied (the launcher's *Reset* action). The full
procedure, including the four other places a deletion leaves stale, is in
[REVS.md](REVS.md) and the maintainer notes for it.

## 8. Definition of done

1. `node tools/selfcheck.mjs` — exit 0 (the drop-in contract: folder rule, discovery, the
   layout example still anchors).
2. `LCLITE_ROOT=<install> node tools/lclite.mjs apply --check` → `✗0`, and
   `node tools/doctor.mjs` → exit 0.
3. `node tools/matrix.mjs` → every declared revision still applies (a new hunk on the
   primary can expire a revision that inherits it).
4. `bash tools/acceptance.sh` → pristine clones at the pinned revs reproduce the live
   tree byte-for-byte, and the converge round-trip is byte-stable.
5. TypeScript touched? `./node_modules/.bin/tsc --noEmit -p tsconfig.json` in the
   install's `webclient/` clean, and `node tools/lclite.mjs build` run.
6. Nontrivial logic? A bun harness beside the mod (`mods/<mod>/tools/<x>_test.ts`) that
   runs the REAL shipped payload.
7. `mods/<mod>/README.md` updated in the same commit as any behaviour change.
8. Committed **in this repo only** — never the modded `webclient/`/`engine/` trees
   (rule 6).

Then play it: gameplay and pixel-level feel is verified in a live client, not by a
harness. `::help` on a dev world is the dialogue test bench, and the browser recipes for
driving a real client are in the maintainer's `lost-city-webclient-tweaks` notes.
